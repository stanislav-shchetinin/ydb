# RFC: ограничение фоновой нагрузки от backup-таблеток в Hive

**Статус:** Draft  
**Дата:** 2026-08-28  
**Компонент:** YDB Hive  
**Связанные подсистемы:** SchemeShard, DataShard, BlobStorage

## Краткое описание

При создании export/backup операций SchemeShard создаёт backup-копии таблиц с большим числом DataShard-таблеток. Массовый запуск этих таблеток создаёт кратковременный всплеск управляющего и системного трафика: одновременно выполняются tablet boot, чтение служебного состояния, регистрация на нодах, обмен по Interconnect и обработка событий в Hive.

Предлагаются два дополняющих направления: уменьшить накладные расходы управляющих запросов и ограничить фоновую tablet/storage работу:

1. bulk create/delete между SchemeShard и Hive: ограниченные пачки, с отдельным рассмотрением удаления backup-объекта по `(OwnerId, ObjectId)`;
2. отдельная логическая очередь запуска backup-таблеток;
3. token bucket для ограничения среднего темпа запуска;
4. глобальные и per-node лимиты одновременно стартующих backup-таблеток;
5. приоритет foreground-таблеток над backup-таблетками;
6. существующие общие лимиты Hive как жёсткая верхняя граница суммарной нагрузки.

Отдельная фаза pacing ограничивает удаление backup-таблеток. Для удаления также используются две очереди, но foreground и backup операции разделяют одно общее окно `MaxDeleteTabletInProgress`. Backup-удаления могут занимать только ограниченную долю этого окна.

Решение намеренно не пытается регулировать чтение пользовательских данных, выгрузку в S3 и compaction borrowed parts. Эта работа выполняется в DataShard/BlobStorage и не может надёжно управляться через скорость boot в Hive.

## Мотивация

### Наблюдаемая проблема

Export большой базы может одновременно создать тысячи backup DataShard-таблеток. Текущая boot queue Hive ограничивает размер одного прохода и число стартующих таблеток на ноде, но не задаёт средний темп запуска. Если доступна ёмкость, последовательные проходы очереди выполняются практически без паузы.

В результате возникают:

- массовые tablet boot и init-чтения;
- всплеск событий в Hive и Local;
- дополнительный трафик по Interconnect;
- кратковременная конкуренция за CPU, memory и actor pools;
- рост latency пользовательских запросов и системных операций;
- конкуренция backup-таблеток с foreground-таблетками при восстановлении нод или кластера.

При завершении export возникает похожий всплеск удаления: большое количество backup-таблеток одновременно блокирует и удаляет tablet storage.

### Почему недостаточно уменьшить boot priority

Приоритет определяет порядок обработки только при наличии конкуренции в одной очереди. Если foreground-очередь пуста, тысячи backup-таблеток всё равно будут запущены максимально быстро. Для ограничения нагрузки нужен admission control, ограничивающий throughput и число операций in flight.

### Граница эффективности Hive

Export выполняется в несколько стадий:

1. SchemeShard создаёт backup-таблицы и их таблетки.
2. Hive запускает созданные таблетки.
3. CopyTable конфигурирует destination DataShard'ы и ждёт завершения общей consistent-copy операции.
4. SchemeShard запускает backup-транзакции на шардах, которые читают данные и выгружают их во внешнее хранилище.
5. После export backup-таблицы удаляются, а исходные DataShard'ы могут выполнять compaction возвращённых borrowed parts.

Backup-таблетки могут быть созданы SchemeShard заранее, до основной операции `CopyTable`. Для Hive момент создания не меняет классификацию и правила запуска: любая таблетка с persisted-признаком `IsBackup` обрабатывается как фоновая. Порядок и темп предварительного создания находятся вне scope этого RFC.

Hive управляет созданием метаданных таблеток, их запуском и Hive-частью удаления; bulk оптимизирует управляющий обмен на этом пути. Замедление boot сдвигает начало стадии 4, но не уменьшает её concurrency: после завершения общего `CopyTables` backup-транзакции могут быть отправлены всем таблицам и их шардам одновременно.

Поэтому данный RFC описывает три локальные задачи:

- сокращение накладных расходов create/delete обмена SchemeShard ↔ Hive;
- сглаживание boot/control-plane spike;
- сглаживание Hive/BlobStorage control-plane spike при удалении.

Он не является полным решением ограничения ресурсоёмкости export.

## Цели

- Сократить число управляющих create/delete запросов и накладные расходы их обработки через bulk API.
- Ограничить средний темп запуска backup-таблеток.
- Ограничить глобальное и per-node число одновременно стартующих backup-таблеток.
- Не позволять backup-работе задерживать запуск foreground-таблеток при наличии конкуренции.
- Сохранить существующие общие лимиты Hive как hard limits.
- Не допустить spin loop и чрезмерной частоты транзакций Hive.
- Обеспечить корректное поведение при restart Hive и динамическом изменении конфигурации.
- Добавить наблюдаемость, достаточную для настройки и безопасного rollout.
- Ограничить долю backup-удалений, не увеличивая общий deletion concurrency.

## Не цели

- Ограничение числа одновременно выполняющихся backup-транзакций в DataShard.
- Ограничение чтения исходных таблиц, PDisk/VDisk I/O или S3 bandwidth.
- Управление compaction borrowed parts.
- Пейсинг создания таблеток и запросов выбора storage groups.
- Изменение поведения tablet balancer.
- Гарантия завершения backup при постоянно исчерпанной foreground capacity.
- Детальный дизайн изменений SchemeShard/DataShard. Для bulk описывается необходимый контракт и отдельная задача интеграции вызывающей стороны.

## Термины

- **Foreground tablet** — таблетка, не помеченная `IsBackup`.
- **Backup tablet** — лидер таблетки, для которого persisted-признак `IsBackup` установлен SchemeShard.
- **Starting** — volatile-состояние таблетки от принятия решения о запуске до подтверждения успешного старта или выхода из этого состояния.
- **Rate limit** — ограничение среднего числа новых запусков или удалений в секунду.
- **In-flight limit** — ограничение числа уже начатых, но не завершённых операций.
- **Hard limit** — ограничение, которое не снимается из-за возраста записи или нагрузки на очередь.

## Предлагаемое решение

### 1. Bulk create/delete: уменьшение числа управляющих запросов

Первым направлением оптимизации предлагаются пакетные операции между SchemeShard и Hive. Они уменьшают накладные расходы на отдельные сообщения и их обработку; boot/delete pacing ниже ограничивает темп и параллелизм самой работы. Это дополняющие, а не взаимоисключающие механизмы. Bulk — планируемое расширение, ещё не реализованное в подготовленном патче pacing.

#### Что уже есть

- `TEvCreateTablet` описывает одну таблетку; SchemeShard передаёт её `Owner/OwnerIdx`, `ObjectId` и `IsBackup`.
- `TEvDeleteTablet` и ответ Hive уже поддерживают список `ShardLocalIdx`. Но текущий `TShardDeleter::SendDeleteRequests` отправляет по одному запросу на шард, а `TTxDeleteTabletReply` в SchemeShard содержит проверку `ShardLocalIdxSize() == 1`. Одного объединения запросов недостаточно: нужно согласованно изменить обработку ответов, ретраев и redirect.
- `TEvDeleteOwnerTablets` удаляет таблетки всего owner и блокирует дальнейшее создание от него. Это не замена удалению одной backup-таблицы по `ObjectId`.

#### Ожидаемый эффект

При размере пачки `B` число запросов и ответов для `N` таблеток можно сократить примерно с `N` до `ceil(N / B)` без учёта ретраев. Это может уменьшить нагрузку на SchemeShard/Hive и CPU Interconnect, если существенна стоимость обработки отдельных сообщений. Объём описаний таблеток и их результатов остаётся `O(N)`; снижения сетевых байтов в `B` раз не обещается.

Число транзакций Hive уменьшится только при пакетной обработке метаданных внутри ограниченных транзакций. Простая оболочка, разворачиваемая в `N` прежних транзакций, экономит главным образом внешний обмен. Число tablet boot, init-чтений, stop и block/delete-storage операций само по себе не сокращается. Поэтому bulk не гарантирует исчезновения всплеска: быстрое наполнение очередей может даже сделать последующий всплеск плотнее.

#### Bulk create

- Передавать ограниченный список описаний таблеток с сохранением существующей идентичности `(Owner, OwnerIdx)`, привязки к объекту, storage bindings и `IsBackup` для каждого элемента. Размеры запроса и ответа ограничивать и по количеству элементов, и по байтам; ограничивать также число запросов in flight.
- Группировать запросы по целевому Hive и owner. Возвращать сопоставление `OwnerIdx -> TabletId/status`, отдельно обрабатывать частичный успех, отсутствие storage, redirect и ретраи. Повтор запроса не создаёт дубликаты; конфликтующие параметры одного ключа требуют явной проверки.
- Обрабатывать метаданные ограниченными пачками, не одной транзакцией на десятки тысяч таблеток. Успешные элементы попадают в обычный путь boot admission с классификацией `IsBackup`; bulk не запускает всю пачку в обход очереди.
- Отличать принятие запроса и создание метаданных от готовности таблетки. Не ослаблять существующий контракт готовности для `PrepareCopyTable/CopyTable`.

#### Bulk delete: список и ObjectId

Минимальный шаг — использовать существующий списочный `TEvDeleteTablet` ограниченными пачками, доработав вызывающую сторону. Пачки должны учитывать owner и Hive-владельца; при миграции нельзя считать весь пакет успешно удалённым из-за результата одного элемента.

Следующий вариант — удаление целого backup-объекта по полному ключу Hive `(OwnerId, ObjectId)`. SchemeShard сейчас передаёт в `ObjectId` локальный PathId destination-объекта; один `ObjectId` без owner не является достаточным селектором. Это позволяет не передавать полный список шардов в исходной команде, но требует нового жизненного цикла групповой операции:

- Объект должен обозначать именно удаляемую backup-копию, а не исходную таблицу. Нужны проверка владельца и backup-класса, запрет неоднозначного/default-ключа и отказ при нарушении контракта, а не расширение области удаления.
- До обхода таблеток сохраняется намерение удалить объект и закрывается admission новых create/rebind для него. Обрабатываются pending create и поздние повторы запросов; защита должна переживать restart и сохраняться после завершения удаления, пока поздний create ещё возможен. Если ключ объекта переиспользуется, требуется идентификатор его инкарнации. Один повторный поиск по текущему `ObjectId` не даёт такой гарантии.
- Нужен индекс принадлежности таблеток объекту либо другой ограниченный способ перечисления без полного сканирования Hive на каждом проходе. Обход, изменения метаданных и stop-события выполняются порциями; прогресс восстанавливается после restart. Миграция в другой Hive, split/merge и отмена export не должны приводить к пропуску или захвату чужих таблеток.
- Принятие операции после durable-записи намерения и завершение очистки — разные статусы. Hive должен явно принять ответственность за продолжение удаления; повтор команды идемпотентен. Ответ `OK` существующего delete-пути также не означает, что физическая очистка storage уже закончилась.
- Каждая таблетка проходит через существующий lifecycle удаления и общий deletion window с backup-ограничениями. Один bulk-запрос не считается одним in-flight удалением для тысяч таблеток; слоты учитываются по таблеткам и удерживаются на ретраях.

Для MVP bulk delete предпочтителен существующий списочный протокол. Удаление по `ObjectId` имеет смысл как следующий шаг после согласования object-level fencing, восстановления и маршрутизации; заменять им список без этих гарантий опасно.

#### Граница работ и проверка эффекта

RFC описывает Hive API и его контракт с вызывающей стороной. Для эффекта bulk необходима отдельная интеграция в SchemeShard; детальный дизайн `PrepareCopyTable/CopyTable` здесь не меняется. Доставлять bulk на старый Hive без проверки поддержки нельзя; нужен совместимый fallback на прежний протокол.

Сравниваются четыре режима: baseline, только bulk, только pacing, bulk + pacing. Измеряются число/размер create/delete сообщений, число и длительность транзакций обеих сторон, CPU/очереди actor pools и IC pool на нодах SchemeShard/Hive, пользовательский p99, число одновременных boot/delete и общее время export. Это отделит экономию управляющего обмена от сглаживания tablet/storage работы.

### 2. Классификация backup-таблеток

Источником истины является существующий persisted-признак `IsBackup`, переданный SchemeShard при создании таблетки.

Интеграционный контракт со SchemeShard:

- предварительно созданные destination-таблетки сразу получают `IsBackup`;
- при переиспользовании подготовленной таблетки в `CopyTable` признак сохраняется;
- недостающие после split таблетки также создаются с `IsBackup`;
- лишние после merge таблетки удаляются как backup-таблетки и попадают под ограничения backup delete.

Контракт не предусматривает переключения уже существующей tablet family между backup и foreground: повторные запросы SchemeShard должны сохранять её `IsBackup`. Переклассификация в этом RFC означает изменение маршрута очереди при enable/disable pacing, а не изменение persisted-признака таблетки.

Для follower используется признак лидера. Это сохраняет единое решение для tablet family, хотя текущий export обычно создаёт backup-таблетки без followers.

Классификация применяется в точке добавления таблетки в boot queue и в точке постановки удаления. Она не должна зависеть от tablet type, поскольку backup и foreground таблетки имеют одинаковый тип `DataShard`.

### 3. Две логические boot-очереди

Hive поддерживает два класса ожидающих запусков:

- main boot queue для foreground и системных таблеток;
- backup boot queue для `IsBackup`.

В одном проходе сначала обрабатывается main queue. После неё Hive может обработать backup queue, если осталась общая capacity.

Если после прохода main ready queue всё ещё непуста, backup-проход пропускается, а main queue перепланируется. Таким образом, ограничение `MaxBootBatchSize` не превращается в возможность запустить background работу впереди уже ожидающей foreground работы.

Backup-запуски:

- не расходуют `MaxBootBatchSize`, выделенный main queue;
- учитываются собственным ограничением числа просмотренных записей за проход;
- всегда подчиняются существующему общему per-node `MaxTabletsScheduled`;
- не запускаются, если main queue остановилась из-за исчерпания общей start capacity.

Обработка обоих классов может выполняться внутри одного `TTxProcessBootQueue`. Это уменьшает число actor events при одновременной работе очередей, но не является требованием корректности.

### 4. Token bucket для backup boot

Для ограничения среднего темпа используется token bucket:

```text
tokens = min(burst, tokens + rate * elapsed)
rateBudget = floor(tokens)
```

Один токен списывается при реальной попытке выбрать ноду и запустить существующую, ещё не запущенную таблетку. Устаревшая запись очереди токен не расходует.

Начальный бюджет — отдельная политика восстановления, а не обязательное свойство token bucket. Небольшой полный bucket допустим, если такой burst безопасен и соблюдены все in-flight limits. В этой реализации выбран консервативный вариант: один токен после каждого старта Hive. Это не позволяет серии рестартов каждый раз восстанавливать полный configured burst. После обычного простоя работающий Hive может накопить до `burst` токенов.

Token bucket должен корректно обрабатывать floating-point rounding. При вычислении следующего пробуждения используется минимальная задержка, исключающая zero-delay или microsecond spin.

#### Частота пробуждений

Пробуждение рассчитывается по дефициту токенов, а не по фиксированному периоду 100–500 мс. При малом rate достаточно дождаться следующего токена. При большом rate бюджет группируется в пачки:

```text
targetTokens = min(burst, max(1, rate * 10ms))
delay = max(1ms, (targetTokens - tokens) / rate)
```

Расчёт delay применяется, когда нет даже одного целого токена. За проход расходуется доступный бюджет с учётом in-flight и scan limits. События изменения состояния могут инициировать проход раньше таймера; токены при этом по-прежнему обязательны.

Константы первой реализации: целевой интервал накопления пачки 10 мс, минимальная задержка таймера 1 мс. Это ограничивает частоту timer-driven проходов и не заставляет ждать 500 мс при маленьком burst. Если `rate > burst / 1ms`, таймерный путь физически не обеспечивает configured rate: rate является верхней границей, а не гарантией throughput. Для больших rate нужно выбирать соразмерный burst, затем проверять нагрузку на Hive. Пробуждения объединяются; устаревшие таймеры не должны создавать дополнительные активные циклы.

### 5. Ограничения числа стартующих таблеток

Backup boot разрешён только при одновременном выполнении условий:

```text
backupStartingGlobal < MaxBackupTabletsStarting
backupStartingOnCandidateNode < MaxBackupTabletsStartingPerNode
allStartingOnCandidateNode < MaxTabletsScheduled
rateBudget > 0
```

Итоговый бюджет прохода:

```text
backupBudget = min(
    rateBudget,
    MaxBackupTabletsStarting - backupStartingGlobal,
    batchScanBudget
)
```

Per-node limit проверяется при выборе candidate node. Нода, достигшая backup-лимита, исключается из кандидатов, но поиск продолжается на остальных нодах.

Счётчики обновляются централизованно при смене volatile state. Это исключает расхождение между несколькими путями завершения старта, отключением ноды и удалением таблетки.

Все лимиты являются hard limits и никогда не обходятся по таймеру. Они проверяются при допуске новой работы. При уменьшении лимита или включении pacing уже начатые операции не прерываются: новые не допускаются, пока фактический in-flight не опустится ниже нового предела. Общий per-node `MaxTabletsScheduled` действует независимо от backup-лимита.

### 6. Foreground priority и отсутствие fail-open aging

Foreground queue всегда обрабатывается первой. Backup использует только capacity, оставшуюся после foreground scheduling.

Если foreground workload постоянно исчерпывает start capacity, backup может не продвигаться. Это намеренное QoS-поведение: доступность пользовательских таблеток важнее завершения фонового export.

Для контроля starvation добавляются:

- метрика возраста старейшей backup-записи;
- warning/alert при превышении операционного порога;
- возможность отменить или перепланировать export на уровне вызывающей подсистемы.

Возраст записи не снимает rate, global, per-node или общие hard limits. В частности, не вводится режим, который после `MaxDelay` принудительно запускает backup на перегруженной или полностью занятой ноде.

### 7. Очереди ready, deferred и wait

Строгий FIFO не используется как единственный источник готовых записей, поскольку одна таблетка с будущим `PostponedStart` может заблокировать всю backup queue.

Логически разделяется состояние; три конкретных типа контейнеров не являются требованием интерфейса:

- `BackupReadyQueue` — записи, готовые к попытке запуска;
- `BackupDeferredQueue` — записи с известным `PostponedStart`, упорядоченные по времени готовности;
- `BackupWaitQueue` — записи, для которых нет допустимой ноды по устойчивым ограничениям размещения.

Каждый проход ограничивает число просмотренных записей. При наступлении ближайшего `PostponedStart` записи возвращаются в ready queue. Wait queue пересматривается при изменении состава/состояния нод и страховочным timer tick с периодом `ResourceChangeReactionPeriod`.

В реализации ready — deque, deferred — упорядоченный по времени контейнер, wait — отдельная очередь. Переносы из deferred/wait также ограничены `MaxBootBatchSize`. Для foreground отложенные записи отделены от ready: будущий `PostponedStart` не должен создавать ложную foreground saturation. FIFO сохраняется среди готовых backup-записей, но не блокирует обход отложенных.

Foreground followers, ожидающие старта лидера без будущего `PostponedStart`, сохраняют event-driven retries: статус лидера немедленно будит их обработку. Между проходами они хранятся отдельно от ready. На событие изменения состояния или страховочный таймер формируется раунд повторной проверки; он обрабатывается ограниченными пачками, а снова заблокированные записи не попадают в тот же раунд. Это исключает непрерывный self-send даже при `MaxBootBatchSize = 1` и не создаёт ложную foreground saturation после завершения проверки.

Возраст старейшей записи учитывается по всем backup-состояниям, включая deferred/wait, без полного сканирования очередей на каждом проходе.

Просроченные deferred records не создают отдельный частый timer loop при закрытом admission: они ждут bounded continuation, изменения capacity или страховочного пробуждения. При этом просроченная backup-запись не скрывает будущий deadline foreground-записи.

Enqueue time хранится отдельно для метрик и не участвует в снятии hard limits.

### 8. Размещение

В MVP используются существующий `FindBestNode`, общие resource restrictions Hive и новый per-node backup-start limit.

Отдельный запрет размещения по глобальному p90 node usage не вводится. Текущий `NodeUsage` отражает compute/memory/actor-pool нагрузку, но не PDisk/VDisk pressure и не нагрузку конкретных storage groups. Такой сигнал недостаточно точно соответствует основной нагрузке export.

Адаптивное ограничение по нагрузке может быть добавлено отдельным RFC после появления измерений и подходящего сигнала с hysteresis.

### 9. Tablet balancer

В рамках этого RFC balancer не изменяется:

- backup tablets не получают `POLICY_IGNORE`;
- их balancer weight не увеличивается;
- работающая backup-таблетка не перемещается только ради снижения фоновой нагрузки.

`POLICY_IGNORE` опасен тем, что при перегруженной backup-нагрузкой ноде балансер может начать перемещать foreground-таблетки. Предпочтительное перемещение самих backup-таблеток также не принимается без доказательства, что restart не создаёт повторное чтение, upload amplification и дополнительную нагрузку.

Если потребуется preemption backup-work, оно должно проектироваться как отдельное явное поведение, а не как побочный эффект балансировки.

### 10. Динамическая конфигурация

Минимальная конфигурация boot pacing:

```text
BackupBootPacingEnabled
BackupBootRate
BackupBootBurst
MaxBackupTabletsStarting
MaxBackupTabletsStartingPerNode
```

При применении и перед использованием проверяются настройки limiter: конечный `rate` в диапазоне [1e-6, 1e9] операций/с, конечный `burst` в диапазоне [1, 1e9], положительные global/per-node limits. Диапазоны ограничивают также преобразования floating-point в целочисленный бюджет и timer duration. Backup per-node limit не отменяет меньший общий `MaxTabletsScheduled`.

Невалидная конфигурация не выключает pacing: соответствующий backup-путь перестаёт допускать новые операции (fail closed), Hive пишет ошибку, foreground продолжает работать. Это локальная runtime-проверка, а не транзакционный отказ публикации конфигурации в Console. Подтверждение config notification означает получение конфигурации, а не обещание прогресса backup. Исправление настроек возобновляет обработку. Нужна операторская проверка активных значений перед rollout.

При включении pacing старые main records переклассифицируются лениво: перед попыткой запуска проверяется текущий флаг и `IsBackup`, и backup-запись переносится в paced queue. Это относится также к main wait/deferred records. Переход не сканирует весь backlog в обработчике конфигурации; миграционные записи расходуют ограниченный scan budget main-прохода, но никогда не запускаются без backup limiter.

При отключении backup records ограниченными порциями переносятся в main queue с сохранением wait/deferred state. Изменение конфигурации будит обработку очередей. Аналогичные правила действуют для удаления; класс уже начатого удаления сохраняется до его завершения.

Начальные значения при включении: boot rate 10/с, burst 10, global limit 16, per-node limit 2; delete rate 10/с, burst 10, backup limit 16 внутри общего окна. Оба флага по умолчанию выключены. Эти значения — отправная точка тестирования, не обещание безопасного production SLO.

### 11. Restart и rollback

После restart Hive очередь восстанавливается из persisted tablet state и `IsBackup`.

Инварианты после восстановления:

- global и per-node starting counters пересобраны из фактического volatile state либо начинают с заведомо безопасного состояния;
- token bucket не стартует с большим burst;
- backup tablets не теряются между ready/wait состояниями;
- correctness не зависит от volatile enqueue time;
- откат на версию без pacing сохраняет корректность таблеток, хотя QoS возвращается к прежнему поведению.

### 12. Пейсинг удаления backup-таблеток

Пейсинг удаления реализуется отдельной фазой после подтверждения, что Hive/BlobStorage deletion control plane является существенной частью завершающего всплеска.

#### Общий лимит

Foreground и backup deletions разделяют существующий общий hard limit:

```text
totalDeleteInFlight <= MaxDeleteTabletInProgress
backupDeleteInFlight <= MaxBackupDeleteInProgress
```

`MaxBackupDeleteInProgress` задаёт максимальную долю общего окна, которую может занять backup. Например, при общем лимите 100 и backup limit 16 не меньше 84 слотов всегда остаются доступными foreground deletion после завершения уже начатых операций.

Не создаётся второе независимое окно поверх `MaxDeleteTabletInProgress`.

#### Приоритет и rate

- foreground delete queue обслуживается первой;
- backup delete queue использует оставшуюся общую capacity;
- backup deletions дополнительно ограничены отдельным token bucket;
- возраст очереди не снимает hard limits.

#### In-flight state

Каждая начатая логическая операция удаления учитывается вместе с её классом:

```text
tabletId -> foreground | paced-backup
```

Один слот покрывает блокировку storage, удаление и все их ретраи. Ошибка или повторная попытка не освобождает слот и не занимает второй. Освобождение выполняется только для известной завершившейся операции. Duplicate, stale или неизвестный результат не должен менять чужие счётчики или удалять не относящуюся к операции таблетку.

Отдельный `generation/requestId` не обязателен, пока для данного TabletId существует только одна необратимая логическая операция удаления, TabletId не переиспользуется, а ответы старой инкарнации Hive адресованы её прежнему ActorId. Эти условия являются частью контракта. Если протокол допускает независимую новую операцию с тем же идентификатором, понадобится идентификатор операции; одного TabletId будет недостаточно.

После restart deleting tablets заново классифицируются по persisted `IsBackup`, а in-flight state восстанавливается или безопасно переигрывается согласно существующей idempotency удаления.

#### Ограничение эффекта

Hive pacing управляет блокировкой и удалением tablet storage. Он не управляет compaction borrowed parts на исходных DataShard'ах. Поэтому успех этой фазы оценивается отдельно от общего disk spike после export.

## Наблюдаемость

Gauges первой реализации:

- `BackupBootQueueSize` — ready + deferred;
- `BackupBootDeferredQueueSize` — отложенная часть;
- `BackupWaitQueueSize` — ожидание допустимой ноды;
- `BackupTabletsStarting`;
- `BackupBootOldestDelayMs` — возраст по ready/deferred/wait;
- `BackupDeleteQueueSize`;
- `BackupTabletsDeleting` — операции, допущенные как paced-backup, внутри общего окна; уже начатые при выключенном флаге удаления остаются только в total;
- `BackupDeleteOldestDelayMs`;
- `TabletsDeleting` — суммарный in-flight обоих классов.

Cumulative counters:

- `BackupBootAttempts`, `BackupTabletsStarted`, `BackupBootPlacementFailed`;
- `BackupBootStaleRecords`, `BackupBootDeferred`, `BackupBootWaitingForNode`;
- `BackupBootForegroundLimit`, `BackupBootRateLimit`, `BackupBootGlobalLimit`, `BackupBootPerNodeLimit`, `BackupBootTotalLimit`;
- `BackupDeleteAttempts`, `BackupDeleteCompleted`, `BackupDeleteRetried`;
- `DeleteUnknownCompletions` — неизвестные и повторные результаты обоих классов.

`BackupTabletsStarted` считает успешно инициированные старты, а не переходы в RUNNING. Ошибки уже начатого boot дополнительно видны в существующих tablet/status метриках. Throttling counters считают проверки/отказы, а не уникальные таблетки; per-node counter считает отклонённые candidate nodes.

`BackupDeleteAttempts` считает допуски новых логических удалений, а `BackupDeleteRetried` — начатые повторные block/delete-storage попытки внутри уже занятого backup-слота.

Фактический rate вычисляется на дашборде как производная соответствующего cumulative counter; отдельный целочисленный gauge `EffectiveRate` не вводится. На monitoring page доступны активная конфигурация и размеры очередей; JSON также показывает per-node starting counts. Причины throttling доступны через tablet counters. Операторские графики и alerts на длительное ожидание настраиваются при rollout.

## Критерии успеха

До rollout задаются численные SLO. Как минимум измеряются:

- число и размер create/delete запросов и ответов, размер пачек, количество и длительность транзакций SchemeShard/Hive;
- CPU/очереди IC и actor pools при одинаковом объёме работ для baseline, bulk, pacing и их комбинации;
- изменение p99 пользовательских запросов во время стадии boot;
- latency запуска foreground-таблетки при большой backup queue;
- максимальное global и per-node число backup tablets в `STARTING`;
- фактический средний и burst rate;
- длительность предварительного создания backup-таблеток;
- длительность стадии `CopyTables` и время schema locks, чтобы убедиться, что bulk boot вынесен из её критического пути;
- полное время export;
- нагрузка Hive actor/event queue и Interconnect;
- для deletion-фазы — BSC/BlobStorage latency и суммарный deletion concurrency.

Функциональный критерий:

- foreground tablet, добавленная при непустой backup queue, не ждёт rate token backup-класса;
- новый admission не превышает hard limits; при снижении предела уже начатые операции завершаются без preemption;
- backup queue продвигается при наличии свободной общей capacity;
- restart/config toggle не позволяют backlog обойти pacing.

## Риски и проблемы решения

### Крупные bulk-пачки и небезопасный выбор объекта

Слишком большая пачка увеличивает время одной транзакции, память, объём ответа и stop/boot fan-out. Без pacing экономия на сообщениях может усилить следующий всплеск. Нужны лимиты по элементам, байтам и in-flight запросам, ограниченные продолжения и per-tablet admission.

Удаление по одному `ObjectId` без owner, привязки к backup-копии и защиты от позднего create может удалить чужие таблетки или оставить воскресшую копию. Object-level delete требует persisted intent/fence и восстановления прогресса; это дополнительная сложность относительно списочного bulk delete.

### Решение не ограничивает основную export-работу

После завершения `CopyTables` SchemeShard может запустить backup-транзакции на всех шардах. Если основная деградация создаётся чтением и S3 upload, эффект Hive pacing будет ограниченным.

### Увеличение времени предварительного создания и общего времени export

Если SchemeShard создаёт backup-таблетки заранее, низкий boot rate увеличивает длительность `PrepareCopyTable` и общее время export. Основная масса запусков не должна увеличивать время schema lock в `CopyTable`; исключение составляют недостающие после split таблетки, создаваемые в её критическом пути.

Нужны отдельные метрики длительности `PrepareCopyTable`, `CopyTables`, schema lock и общего времени export, а также операционный upper bound. Этот риск нельзя устранять обходом hard limits.

### Starvation при постоянной foreground-нагрузке

Backup может долго не продвигаться, если foreground полностью использует start capacity. Это сознательный выбор QoS. Длительное ожидание должно приводить к alert или отмене export, а не к fail-open запуску.

### Ошибочно выбранные rate и limits

Слишком высокие значения не защитят latency; слишком низкие значительно увеличат время предварительного создания и общее время export. Значения должны подбираться на canary по метрикам, а не становиться активными defaults без измерений.

### Нагрузка на сам Hive

Слишком частые timer events могут превратить pacing в значимый источник Hive transactions. Частота tick и scan budget должны иметь жёсткую нижнюю/верхнюю границу.

### Head-of-line blocking и рост памяти

Миллионы записей требуют bounded processing и предсказуемого memory footprint. Необходимо разделение ready/deferred/wait, а не строгий FIFO с блокировкой всей очереди одной записью.

### Restart и динамический config

Неполная переклассификация backlog, полный burst после restart или неправильное восстановление counters могут временно отключить защиту либо навсегда остановить очередь.

### Duplicate и stale events

Actor events и delete results могут быть повторными или относиться к уже удалённой таблетке. Все счётчики in-flight должны изменяться идемпотентно по учёту известных логических операций.

### Неполный сигнал нагрузки

Hive node usage не отражает PDisk/VDisk и конкретные storage groups. Добавление adaptive rate на этом сигнале может остановить backup по несвязанной причине или не заметить реальную disk overload.

### Взаимодействие с balancer

Даже без изменений балancer может перемещать работающие backup-таблетки. Это следует наблюдать метриками. Автоматическое предпочтение backup как жертв может увеличить повторное чтение и не входит в MVP.

Сохраняется существующее условие планирования обычного balancer: boot queue должна опустеть. Более долгий backup backlog поэтому может откладывать новые плановые проходы tablet/storage balancer. Нужно наблюдать длительность этой задержки и дисбаланс нод; разрешение обычной балансировки при непустой backup queue потребует отдельного решения.

### Ограниченный эффект deletion pacing

Удаление tablet storage — только часть завершающей нагрузки. Compaction returned borrowed parts остаётся вне контроля Hive.

При недоступности BlobStorage ретраи удерживают слоты логических удалений. Это намеренно ограничивает concurrency, но может остановить очередь; освобождать такие слоты по возрасту нельзя. Нужны наблюдение за retry rate, восстановление storage и резерв foreground capacity за счёт backup limit, меньшего общего окна.

## Совместимость

- Для boot/delete pacing новых wire- или persisted-форматов не требуется: используется существующий `IsBackup`.
- Bulk create и object-level delete требуют расширения протокола; object-level delete также требует persisted intent/fence и восстановления прогресса. Списочный delete использует имеющийся wire format, но требует совместимого обработчика ответа SchemeShard. Включение — только после проверки поддержки обеих сторон, с fallback на прежние запросы; rollback object-level delete требует предварительного завершения операций либо версии, понимающей их persisted state.
- Новые config fields являются additive; по умолчанию выключены оба флага pacing.
- Экспериментальные поля `Backup*MaxDelay`, `Backup*MinRate`, `Backup*UserWeight`, настройки адаптации по node usage и `BackupTabletBalancerWeight` сохранены в proto как deprecated для разбора ранее подготовленных конфигураций, но не влияют на поведение. Их нужно удалить из конфигурации тестового кластера.
- `MaxBackupTabletsStartingPerNode = 0` больше не означает отключение лимита: при включённом pacing это невалидное значение. Для миграции нужно явно задать положительный предел либо использовать default 2.
- Старые версии Hive игнорируют неизвестные config fields и сохраняют прежнее QoS-поведение.
- Откат изменений pacing не должен влиять на correctness export или tablet lifecycle; исчезает только pacing. Для bulk отдельно соблюдаются условия совместимости протокола и persisted state, перечисленные выше.
- Dynamic enable/disable использует ограниченные переносы и проверку классификации перед допуском операции.

## Rollout

Bulk включается независимо: сначала ограниченные create/delete пачки с совместимыми ответами и ретраями, затем — при отдельном подтверждении необходимости — object-level delete. До этого снимаются baseline и результаты четырёх режимов сравнения. Следующая последовательность относится к pacing:

1. Добавить метрики без изменения поведения и снять baseline.
2. Включить boot pacing на тестовом кластере с консервативными значениями.
3. Проверить функциональные инварианты, длительность предварительного создания, `CopyTables` и общего export.
4. Выполнить canary на одном production database/domain.
5. Сравнить пользовательский p99, foreground boot latency и время export.
6. Постепенно расширять rollout.
7. Delete pacing включать отдельно, после независимой оценки его эффекта.

Rollback pacing выполняется отключением соответствующего feature flag. При отключении все backup records переносятся в общие очереди; это не отменяет уже принятые object-level delete операции.

## Декомпозиция задач

### Этап 0. Baseline и контракты

#### 0.1. Разметить стадии export

- Добавить или проверить метрики длительности create/copy/boot/transfer/drop.
- Отделить boot spike от DataShard backup traffic.
- Зафиксировать baseline p99 и Interconnect/Hive load.

**Результат:** подтверждено, что boot является самостоятельным значимым источником деградации.

#### 0.2. Проверить контракт предварительного создания и CopyTable

- Определить DDL, блокируемые состоянием copying.
- Проверить cancellation/retry/restart при долгом предварительном запуске destination shards.
- Убедиться, что bulk boot не удерживает schema lock `CopyTable`.
- Задать допустимый бюджет увеличения `PrepareCopyTable` и общего времени export.

**Результат:** выбран rate, не нарушающий schema-operation SLO.

### Этап 1. Bulk create/delete

#### 1.1. Контракт и ограниченный bulk create

- Определить per-item identity, статусы, partial success и готовность таблеток.
- Задать пределы элементов/байтов запроса, ответа, транзакции и запросов in flight.
- Реализовать Hive API и отдельно интегрировать отправку/обработку результатов в SchemeShard.
- Сохранить обычный boot admission и `IsBackup`; проверить retry, restart, redirect и несовместимого peer.

#### 1.2. Списочный bulk delete

- Переиспользовать списочный `TEvDeleteTablet`, группируя по owner/Hive.
- Изменить одношардовый контракт ответа SchemeShard, его учёт, ретраи и redirect.
- Ограничить обработку пачки и stop fan-out; сохранить per-tablet deletion slots и pacing.
- Проверить partial failure, повтор/потерю ответа, restart и отсутствие преждевременного завершения.

#### 1.3. Удаление по ObjectId — отдельный подэтап

- Зафиксировать полный ключ backup-объекта, защиту от чужих объектов и переиспользования ключа.
- Спроектировать persisted delete intent/fence, обработку pending/поздних create и восстановление прогресса.
- Обеспечить ограниченное перечисление таблеток, обработку миграции и split/merge.
- Проверить concurrent create/delete, restart между пачками и повтор команды после завершения.

#### 1.4. Сравнение bulk и pacing

- Сравнить четыре режима: baseline, bulk, pacing, bulk + pacing.
- Сравнить сообщения, транзакции, IC/actor CPU, p99 и время export при одинаковом числе шардов и одинаковых лимитах.
- По измерениям выбрать размер пачки и решить, оправдан ли переход от списка к `ObjectId`.

### Этап 2. Boot pacing MVP

#### 2.1. Классификация и структуры очередей

- Маршрутизировать `IsBackup` в backup queue.
- Разделить ready/deferred/wait состояния, не привязывая контракт к конкретным контейнерам.
- Ограничить scan budget одного прохода.
- Исключить head-of-line blocking.

#### 2.2. Реализовать token bucket

- Rate и burst.
- Безопасное floating-point округление.
- Ограниченная частота timer tick.
- Без большого initial burst после restart.
- Unit tests граничных значений.

#### 2.3. Реализовать global/per-node admission

- Global backup starting counter.
- Per-node backup starting counter.
- Обновление в единой точке volatile-state transition.
- Продолжение поиска по другим нодам при достижении per-node cap.
- Сохранение общего `MaxTabletsScheduled` как hard limit.

#### 2.4. Интегрировать с main boot loop

- Main queue обрабатывается первой.
- Backup использует оставшуюся capacity.
- Backup имеет собственный batch/scan budget.
- Throttling foreground не обходится background-проходом.

#### 2.5. Dynamic config и restart

- Runtime-проверка полей и fail-closed поведение при невалидной конфигурации.
- Переклассификация существующего backlog при enable.
- Слияние очередей при disable.
- Восстановление после restart Hive.
- Проверка rollback на версию без pacing.

#### 2.6. Метрики и monitoring

- Размеры всех очередей.
- In-flight global/per-node; per-node значения в monitoring JSON.
- Cumulative counters для вычисления фактического rate и диагностики throttling.
- Oldest delay и stale records.
- Отображение active config.

#### 2.7. Тесты boot pacing

- Rate и burst.
- Global и per-node limits.
- Foreground tablet не ждёт backup token.
- Постоянная foreground saturation.
- Deferred head не блокирует ready records.
- No-node/wait-queue recovery.
- Restart Hive с backlog и in-flight starts.
- Enable/disable с уже непустой main queue.
- Stale/duplicate status events.
- Полный регресс Hive tests.

#### 2.8. Нагрузочный тест и canary

- Export таблицы с тысячами шардов.
- Одновременная пользовательская нагрузка.
- Сравнение boot phase p99, total export time и CopyTable lock time.

### Этап 3. Delete pacing

#### 3.1. Подтвердить необходимость

- Измерить долю Hive/BSC deletion traffic в завершающем spike.
- Отделить её от borrowed-parts compaction.

#### 3.2. Разделить delete queues при общем окне

- Foreground и backup queues.
- Единый `totalDeleteInFlight` hard limit.
- Максимальный backup share.
- Foreground priority.

#### 3.3. Добавить delete token bucket

- Отдельные rate/burst.
- Переиспользование проверенного pacer primitive.
- Никакого bypass hard limits по возрасту.

#### 3.4. Сделать completion идемпотентным

- Учёт логических операций удаления по TabletId с сохранением класса и слота на ретраях.
- Duplicate/stale completion не изменяет counters.
- Корректное восстановление после restart.

#### 3.5. Метрики и тесты удаления

- Общий и class-specific inflight.
- Foreground delete при большом backup backlog.
- Проверка `total <= MaxDeleteTabletInProgress`.
- Retry, duplicate result, no-storage tablet, restart Hive.
- Нагрузочный тест BSC/BlobStorage.

### Этап 4. Возможные последующие улучшения

Эти задачи не входят в исходный rollout и требуют отдельного design review:

- adaptive pacing по релевантным IC/PDisk/VDisk сигналам;
- hysteresis/AIMD controller;
- явное pause/preemption для backup work;
- изменения balancer policy;
- pacing создания таблеток;
- ограничение concurrency backup-транзакций в SchemeShard/DataShard.

## Решение, предлагаемое к утверждению

Первым направлением плана является bulk create/delete с ограниченными пачками и отдельным безопасным контрактом удаления по объекту. Это новое расширение RFC, а не заявление о наличии bulk в подготовленном коде. Начать bulk delete предлагается со списочного протокола; object-level delete требует отдельного подэтапа.

Поставка статического boot pacing с двумя классами очередей, token bucket, global/per-node backup limits, общими hard limits и наблюдаемостью остаётся независимой. Bulk не заменяет pacing и требует интеграции SchemeShard. Решение о сочетании механизмов и размерах пачек принимается по измерениям.

Не утверждаются в первой поставке:

- fail-open aging;
- глобальная адаптация по p90 node usage;
- изменение tablet balancer;
- независимое дополнительное окно удаления;
- заявления об ограничении DataShard/S3 backup concurrency.

Delete pacing поставляется отдельной фазой и использует общий deletion hard limit.
