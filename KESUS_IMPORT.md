# Отличия от других схемных объектов

Создание Kesus в SchemeShard восстанавливает только coordination node. Ресурсы рейт лимитера хранятся в его tablet и создаются отдельными запросами. Поэтому после создания схемного объекта нужен отдельный этап восстановления ресурсов; завершать item сразу после создания узла нельзя.

Документ описывает решение, зеркальное [KESUS_EXPORT.md](KESUS_EXPORT.md), на базе `ee2a87b43f3` и снимка незакоммиченных изменений экспорта от 29 октября 2026 года. Импорт и тесты реализованы в отдельном worktree `/tmp/ydb-kesus-import-design`. Сборка и тесты не запускались по договорённости. Замечания к экспортному решению вынесены в [KESUS_EXPORT_REVIEW.md](KESUS_EXPORT_REVIEW.md).

# Решение

Поддерживается импорт Kesus из S3 и FS через существующий серверный import. В обоих случаях используются общий getter и машина состояний SchemeShard. Изменения CLI и чтение старого формата `tools dump` с отдельными `CreateResourceRequest` не входят в эту задачу.

1. Расширить `TSchemeGetter`, чтобы он распознавал Kesus и полностью читал его описание до создания узла.

   Формат файлов совпадает с экспортом:

   | Файл | Содержимое | Обязательность |
   | --- | --- | --- |
   | `metadata.json` | Существующий `TMetadata`: версия, признак permissions | По существующему протоколу импорта |
   | `create_coordination_node.pb` | Текстовый `Ydb::Coordination::CreateNodeRequest` | Обязателен |
   | `rate_limiter_resources.pb` | Текстовый `Ydb::RateLimiter::Resources` | Обязателен, включая пустой набор |
   | `permissions.pb` | Текстовый `Ydb::Scheme::ModifyPermissionsRequest` | По `no_acl` и признаку permissions в metadata |

   Запись Kesus уже добавлена экспортом в `GetXxportProperties`. На стороне импорта дополнительно нужны разрешение `EPathTypeKesus` в `CheckAvailableInImport`, разбор `CreateNodeRequest` и отдельная загрузка контейнера ресурсов. Определять тип по содержимому `scheme.pb` или генерировать SQL не требуется.

   После чтения конфигурации и необходимых ACL getter всегда загружает ресурсы Kesus. Все переходы после ACL, включая `no_acl`, `permissions=0` и допустимое отсутствие ACL в старой metadata, должны вести в эту ветку. Проверки materialized indexes и загрузка changefeeds для Kesus не выполняются.

   Отсутствующий ресурсный файл означает неполный бекап. Нулевая длина также считается ошибкой: проверять её нужно до формирования Range GET, а пустой plaintext — после расшифрования. Корректный пустой набор экспорт записывает как `resources: []` с переводом строки; он разбирается в ноль ресурсов. Сам protobuf-парсер принимает и пустую строку, поэтому одной проверки успешности разбора недостаточно. Непустой синтаксически корректный textproto с пустым контейнером не обязан побайтово совпадать с записью экспортера.

   Для двух новых файлов использовать `google::protobuf::TextFormat::Parser` с запрещёнными неизвестными полями. Общий backup helper `ParseProto` включает `AllowUnknownField(true)`: с ним ошибочное имя поля контейнера может превратиться в успешно прочитанный пустой набор, а неизвестные свойства ресурса — потеряться. Строгий разбор делает неподдерживаемое расширение формата явной ошибкой; существующие правила разбора остальных типов объектов менять не требуется.

   Перед переходом к созданию узла проверить весь контейнер: непустые допустимые пути, тип ресурса, поддерживаемые поля metering, отсутствие повторов и наличие каждого непосредственного родителя. Пути должны уже иметь канонический относительный вид по правилам Kesus; неканонический путь отклоняется, как в публичном RPC. Дубликаты выявляются по каноническому ключу. Затем пересортировать ресурсы лексикографически по `resource_path`. Родитель является префиксом потомка, поэтому окажется раньше него; граф зависимостей не нужен.

   Для публичных полей использовать проверки, эквивалентные `ValidateResource`/`ValidateMetric` в rate-limiter RPC, вынеся общую часть при необходимости. `FillRateLimiterDescription` сам не проверяет отсутствие типа и может отбросить неподдерживаемые `metric_fields`. Числовые ограничения дополнительно проверяет Kesus при добавлении; такая ошибка может оставить уже созданный узел и часть ресурсов.

2. Создавать узел обычной схемной транзакцией и сохранять необходимые данные для возобновления.

   Добавить `CreateKesusPropose` по образцу `CreateTablePropose`: `MakeModifySchemeTransaction`, `ESchemeOpCreateKesus`, `WorkingDir` и имя из `item.DstPathName`, заполнение `TKesusDescription` через `FillKesusDescription`.

   При реализации учтено ограничение `RequiresSinglePartTransaction` у Kesus: автоматическое объединение MkDir и CreateKesus недопустимо. Поэтому сначала в отдельной фазе `CreateKesusParent` создаются недостающие каталоги через `CreateKesusParentPropose`, а в CreateKesus передаются фактический родитель и только имя узла. Если родитель уже существует, отдельный MkDir не отправляется. При конкурирующем создании общего родителя выполняется повтор после коммита, без записи чужого txid в `TxIdToImport`: эта таблица соответствует только одному item на txid.

   Путь назначения берётся только из настроек импорта. `CreateNodeRequest.path` не используется, а `config.path` очищается перед proposal, как это делает экспорт: существующий `CreateKesus` запрещает непустой `config.path`. Новый tablet получает свой настоящий путь во время создания. Старые PathId, TabletId и ResourceId из источника не переносятся.

   ACL и owner применять в proposal через существующие `FillACL`, `FillOwner` и `ChooseAppropriateOwner`, с сохранением `no_acl` и системной политики владельца. Ресурсы затем восстанавливает внутренний актор в рамках уже авторизованного импорта; это не новая пользовательская сессия, которой пришлось бы проходить ACL восстановленного узла.

   В `TImportInfo::TItem` добавить конфигурацию coordination node и контейнер ресурсов. Сохранять оба сообщения, включая наличие пустого контейнера, в новых колонках `Schema::ImportItems` вместе с переходом из `GetScheme` в `CreateSchemeObject`. Расширить `PersistImportItemScheme` и загрузку в `schemeshard__init.cpp`. После этого источником для повторов служит сохранённый набор, а не повторное чтение изменяемого S3/FS.

   Назначение должно быть новым узлом: импорт не объединяет бекап с произвольным существующим Kesus. Для повторного создания сохранить `CreateKesusTxId` до отправки proposal после коммита транзакции SchemeShard. Он хранится отдельно от `WaitTxId`: до принятия proposal последний остаётся `Invalid`. Если reboot произошёл в этом промежутке, восстановить `TxIdToImport` и повторить proposal с тем же `CreateKesusTxId`. Одной подписки на txid недостаточно: существующий обработчик Notify отвечает completion и для неизвестной транзакции, которая могла ещё не начаться. После `StatusAccepted` сохраняется `WaitTxId` и используется обычный `SubscribeTx`.

   Проверять принадлежность узла своей транзакции на всех выходах создания, включая `StatusSuccess`; `PathCreateTxId` чужой операции не принимается за свой. После появления узла сохранить `DstPathId`, а после reboot сверять тип, идентификатор пути и транзакцию создания. Одинаковое имя или конфигурация существующего узла не доказывают, что он принадлежит этому импорту.

   Переход к ресурсам выполняется только после завершения создания Kesus. Общую функцию перехода нужно вызвать и из `OnNotifyResult`, и из ветки `StatusSuccess` в `OnModifyResult`: сейчас первая ветка ожидает таблицу после проверок Topic/SQL, а вторая сразу выставляет `Done`.

3. Новый актор `TKesusResourcesRestorer` восстанавливает ресурсы в созданном tablet.

   Он получает import id, item index, сохранённый `DstPathId` и проверенный контейнер ресурсов. Сам актор не читает S3/FS; загрузка, расшифрование и checksums остаются в getter. Примерная схема работы:

   1. Получить актуальное описание назначения из SchemeShard по `DstPathId`, проверить тип Kesus и извлечь его новый `KesusTabletId`. Узел, удалённый или заменённый другим по тому же пути, означает ошибку, а не новое назначение.
   2. Открыть tablet pipe. Запросить существующие ресурсы через `TEvDescribeQuoterResources` с пустыми фильтрами и `Recursive=true`. При первом запуске узел пуст; при повторе в нём может находиться часть восстановленного набора.
   3. Сопоставить существующие ресурсы с сохранённым контейнером. Совпавшие пропустить, несовпадающий ресурс или лишний путь считать конфликтом. Автоматически изменять или удалять ресурсы не нужно.
   4. Последовательно создавать недостающие ресурсы в порядке `resource_path`: `FillRateLimiterDescription` в новый `TStreamingQuoterResource`, затем `TEvAddQuoterResource`. Следующий запрос отправлять после подтверждения предыдущего. Kesus самостоятельно выдаёт ResourceId и находит родителя по пути.
   5. `SUCCESS` подтверждает создание. При `ALREADY_EXISTS` описать конкретный ресурс и сравнить все экспортируемые свойства. Этот статус сам по себе недостаточен: текущий Kesus сравнивает только DRR и не сравнивает metering.
   6. После подтверждения всего набора закрыть pipe и отправить результат в SchemeShard. Для пустого набора запросов Add нет. При ошибке вернуть путь ресурса и причину.

   Сравнение выполнять семантически по публичному `Resource`, включая metering и optional-поля, без внутренних идентификаторов. Ожидаемое описание нормализовать преобразованием `public → internal → public`, полученное от tablet — тем же публичным представлением. Это учитывает, например, дополнение `metric_fields` стандартными ключами при обратном преобразовании. Сравнивать сериализованные строки protobuf нельзя: порядок map-полей не является частью контракта.

   При разрыве pipe или потере ответа неизвестно, успел ли Add закоммититься. После ограниченного числа повторов подключения/запроса завершаем импорт ошибкой; до исчерпания попыток повторяем сверку с сохранённым набором. Таймауты и ответы связываются с текущей попыткой/запросом, чтобы запоздалое событие не завершило следующую попытку. При завершении или `TEvPoisonPill` pipe закрывается.

4. Добавить отдельное сохраняемое состояние item `RestoreKesusResources`.

   Последовательность: `GetScheme → CreateKesusParent → CreateSchemeObject → RestoreKesusResources → Done`. Значения новых состояний — 9 и 8 соответственно; числовые значения существующих состояний сохранены. Общий import остаётся в `Waiting`, пока выполняются его items.

   Сохранять переход к ресурсам и `DstPathId` до запуска актора. В `Resume` для этого состояния создавать новый restorer. Для первой реализации отдельный `NextResourceIdx` не нужен: актор повторно сверяет весь сохранённый контейнер и добавляет недостающее. Так покрываются потеря ответа последнего Add и reboot до сохранения `Done` без отдельной транзакции SchemeShard на каждый ресурс.

   Actor id хранится только в памяти и учитывается в реестре работающих помощников импорта. Результат принимать только от текущего актора для ожидаемых import id, item index и состояния; после cancel/forget или замены актора поздний ответ игнорируется. Запуск через результат коммита транзакции, регистрация событий в `schemeshard_private.h`/`schemeshard_impl.h` и диспетчеризация нужны так же, как для существующих getter/query executor.

   Обновить общий подсчёт завершённых items и отображение прогресса. Ресурсы можно показывать существующим `PROGRESS_TRANSFER_DATA`, не используя табличный `RestoreTableDataPropose` и статистику DataShard. Новый публичный RPC или progress enum не требуется.

   Ручная отмена, ошибка другого item и завершение SchemeShard должны останавливать restorer вместе с остальными помощниками. Отмена прекращает отправку следующих Add, но не откатывает уже отправленный запрос, который мог закоммититься. После ошибки/отмены допустим частично восстановленный узел; автоматическое удаление узла или ресурсов не входит в решение. Новый импорт в тот же занятый путь не является продолжением отменённого.

5. Сохранить ограничения авторизации публичного rate-limiter API.

   В публичном RPC любое наличие `metering_config`, даже с `enabled=false`, требует `IsAdministrator`. Обычный import проверяет `GenericRead | GenericWrite` на БД; прямое обращение к tablet эту отдельную проверку не выполняет.

   Добавить внутренний признак `CanRestoreRateLimiterMetering`: вычислять его в import RPC тем же `IsAdministrator` по полному токену, передавать в SchemeShard и сохранять в `TImportInfo`/`Schema::Imports`. Не вычислять его из одного `UserSID` или `SanitizedToken`: администратор может определяться членством в группе, а sanitized token предназначен для аудита. Отсутствующее поле означает `false`.

   Если контейнер содержит metering, а разрешения нет, возвращать ошибку авторизации до создания узла. Без metering обычный импорт не требует этой дополнительной привилегии. Признак не является параметром публичных `ImportFromS3Settings`/`ImportFromFsSettings`, который пользователь мог бы выставить сам.

6. Шифрование, контрольные суммы и FS использовать из существующего импорта.

   Для зашифрованного бекапа item IV берётся из `SchemaMapping/mapping.json` через существующий поток `TSchemaMappingGetter`. Вызовы `MaybeDecrypt` получают типы `CoordinationNodeCreate` для конфигурации и `CoordinationNodeCreateRateLimiter` для ресурсов; файловый IV получается как `TEncryptionIV::Combine(itemIV, fileType, 0, 0)`. Номер item повторно не подмешивается.

   Getter уже добавляет `.enc` к именам зашифрованных файлов. Checksums остаются в незашифрованных `<имя>.sha256` и проверяются по исходному plaintext, после расшифрования и до нормализации/пересериализации protobuf. Сохраняются `skip_checksum_validation` и существующее поведение для metadata version 0. Пропуск проверки checksum не делает ресурсный файл необязательным. При наличии ключа, но отсутствии необходимого item IV возвращается ошибка.

   Зашифрованный импорт сохраняет существующее требование общего source prefix и schema mapping. Поддержка шифрования для старого S3-запроса только с `items[].source_prefix`, без общего `source_prefix`, здесь не добавляется.

   Для FS использовать `TGetterSettings::FromImportInfo` и `GetItemSource`: относительный item source дополняется `base_path`, абсолютный путь из mapping уже обработан общей логикой. Файлы ресурсов не перечисляются через ListObjects и не добавляются по одному в metadata. Новые публичные protobuf-сообщения сверх экспортного `Ydb.RateLimiter.Resources` не нужны.

# Изменения

1. `TSchemeGetter` и общие имена файлов

   * Разрешить Kesus в импортном фильтре, разобрать `CreateNodeRequest`, загрузить обязательный `Resources` и добавить соответствующие состояния/обработчики.
   * Проверить размер, формат, иерархию, публичные поля, шифрование и checksums до создания объекта; обойти табличные indexes/changefeeds во всех переходах.
   * Вынести фиксированное имя `rate_limiter_resources.pb` в общее определение для экспортера и импортера. Это отдельный формат от `CreateRateLimiter()` старого `tools dump`.
2. `TImportInfo`, persistence и прогресс

   * Добавить конфигурацию, контейнер, `CreateKesusTxId`, состояния `CreateKesusParent`/`RestoreKesusResources` и actor id; расширить `Schema::ImportItems`, persist/init и вывод состояния.
   * Сохранять разрешение на metering в import целиком; расширить внутренний create-import proto, RPC и `Schema::Imports`.
   * Сохранить числовую совместимость состояний и корректную загрузку старых записей без новых полей. Наличие пустого контейнера не смешивать с отсутствием данных.
3. `TTxProgress` и proposal

   * Реализовать `CreateKesusParentPropose` для недостающих каталогов и `CreateKesusPropose` с ACL/owner, путём назначения и проверкой принадлежности создания этому item.
   * Расширить выделение txid, оба пути завершения создания, `Resume` и приём результата restorer. `Done` выставлять только после восстановления ресурсов.
4. `TKesusResourcesRestorer`

   * Реализовать describe назначения, сверку ресурсов, последовательные Add, полное сравнение при повторе, обработку pipe/retry/timeout и освобождение ресурсов.
   * Подключить исходник и события, остановку при cancel/error/shutdown, защиту от запоздалых результатов. При изменении общего интерфейса сохранить сборку fallback-конфигурации без S3.
5. Тесты серверного импорта в `ut_restore`

   * Export→import для S3 и FS: пустой и непустой набор, несколько уровней и корней, наследуемые настройки, optional-поля, replicated bucket, metering, новый путь назначения.
   * ACL/owner с `no_acl`, permissions 0/1; импорт без metering обычным пользователем и отказ на metering для неадминистратора, включая `enabled=false` и reboot.
   * Шифрование через schema mapping, неправильный ключ/IV, перестановка файлов, повреждённая checksum, пропуск checksum; отсутствие, нулевая длина, повреждённый protobuf и неизвестные поля/опечатка имени `resources`.
   * Несортированный набор, неканонические пути, дубликаты канонических путей, отсутствующий родитель, неподдерживаемые типы/metric_fields и ошибка числовых параметров.
   * Reboot после сохранения файлов, создания узла, Add и последнего Add до сохранения `Done`; потеря ответа, изменение S3 после сохранения контейнера, исчерпание повторов.
   * Совпадающий DRR при отличающемся metering, чужой существующий узел, удаление/повторное создание по тому же имени, чужая конкурирующая транзакция создания.
   * Существующий/отсутствующий вложенный родитель, reboot при создании каталогов и несколько items с общим создаваемым родителем.
   * Cancel на каждой фазе, ошибка соседнего item, поздний результат старого актора и смешанный импорт Kesus/таблиц/Topic/SQL.

# Проверка по коду

Реализация проверена чтением исходников и взаимным ревью отдельных частей. Добавлены интеграционные сценарии в [ut_restore_kesus.cpp](ydb/core/tx/schemeshard/ut_restore/ut_restore_kesus.cpp). C++-сборка и тесты не запускались; результат их выполнения пока неизвестен.

# Ограничения

Восстанавливаются конфигурация coordination node, поддерживаемые публичные свойства ресурсов и ACL. Семафоры, сессии, текущее потребление, старые tablet/resource ids и непубличные свойства не восстанавливаются. В процессе импорта не предполагаются параллельные изменения ресурсов назначения; атомарной публикации всего дерева Kesus этот протокол не обеспечивает.

Один контейнер означает чтение всего набора в память и сохранение его в SchemeShard. Это осознанный выбор для первой реализации, согласованный с экспортом; допустимый объём и поведение большого дерева нужно проверить нагрузочным тестом. При необходимости лимит контейнера вводится согласованно с экспортом, а не молча обрезает ресурсы.

Импорт работает с завершённым, не изменяемым во время чтения бекапом. Сохранение контейнера защищает последующие повторы, но не создаёт общего снимка конфигурации и ресурсов при чтении источника.
