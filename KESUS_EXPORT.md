# Отличия от других схемных объектов

Саму protobuf конфигурацию кесуса можно бекапить без проблем, однако наряду с ней необходимо сохранять и информацию о ресурсах рейт лимитера. Ее можно получить только из самого контроллера кесуса, чей ID хранится в скимшарде в `TPathDescription`.

# Решение

Поддерживается экспорт Kesus в S3 и FS. Изменения CLI не входят в эту задачу.

1. Новый актор `TKesusSchemeUploader` на базе `TExportFilesUploader`. Самостоятельно получает описание кесуса из SchemeShard, обращается к Kesus tablet за полным набором описаний ресурсов рейт лимитера и загружает файлы в S3 или FS в зависимости от настроек экспорта. Все ресурсы сохраняются одним публичным protobuf-сообщением в одном файле с фиксированным именем, например `rate_limiter_resources.pb`. Импорт читает ресурсы из этого файла; перечислять отдельные ресурсы в метадате не требуется.

   Актор во многом будет похож на `TSchemeUploader`. Определить, что создавать нужно именно его, а не обычный `TSchemeUploader`, можно по `SourcePathType` у item экспорта. Примерная схема работы:

   1. На бутстрапе отправка `DescribeScheme` в SchemeShard по исходному `SourcePathId`.
   2. Получение `TPathDescription`, извлечение конфигурации кесуса, прав доступа и `KesusTabletId`. Подготовка публичного `Ydb::Coordination::CreateNodeRequest` по аналогии с `tools dump`, с очисткой `config.path`.
   3. Создание tablet pipe и отправка `TEvDescribeQuoterResources` с пустыми `ResourcePaths` и `ResourceIds` и `Recursive=true`. Такой запрос возвращает полные описания всех ресурсов, включая вложенные.
   4. Получение ответа кесуса, закрытие пайпа, преобразование внутренних описаний ресурсов в публичные `Ydb::RateLimiter::Resource`, обычная лексикографическая сортировка по `resource_path` и заполнение сообщения `Ydb::RateLimiter::Resources`. Родительский путь — префикс дочернего, поэтому окажется раньше него (`a` перед `a/b`); граф зависимостей не нужен.
   5. Подготовка общей очереди загрузки: конфигурация кесуса, права доступа, один файл со всеми ресурсами, метадата и контрольные суммы, если они включены.
   6. Загрузка очереди в выбранное хранилище (S3 или FS) через `TExportFilesUploader`.
   7. Отправка успешного результата в SchemeShard после загрузки всех файлов. При ошибке получения описаний или загрузки возвращается ошибка.

   Обработку ошибок подключения, таймаутов и отмены выполняет сам uploader. Для ожидания ответа Kesus используется отдельное событие таймаута, обрабатываемое только в состоянии ожидания; после перехода к загрузке оно игнорируется. Обычный `TEvWakeup` для этого не используется, поскольку базовый uploader обрабатывает его как повтор отправки файла. При завершении актора открытый tablet pipe закрывается.

2. Для хранения набора ресурсов создать новое публичное protobuf-сообщение `Ydb.RateLimiter.Resources` с полем `repeated Resource resources` в `ydb/public/api/protos/ydb_rate_limiter.proto`. В существующем публичном API есть описание одного ресурса, а `ListResourcesResult` содержит только пути, поэтому готового контейнера с полными описаниями нескольких ресурсов нет. Новый RPC для этого не требуется. Внутренний ответ `TEvDescribeQuoterResourcesResult` в бекап не записывается.

   Каждый элемент контейнера содержит `resource_path` относительно coordination node, настройки алгоритма и metering. Сохраняются только поля, представимые публичным `Ydb.RateLimiter.Resource`; перенос остальных внутренних свойств ресурса не входит в задачу.

   Файл записывается и для пустого набора ресурсов. В этом случае его содержимое — текст `resources: []` с завершающим переводом строки, а не файл нулевой длины. Это допустимое представление пустого repeated-поля в protobuf text. Стандартный `PrintProto` опускает пустое repeated-поле, поэтому такое содержимое формируется явно при отсутствии ресурсов. Контрольная сумма вычисляется по окончательному тексту; шифрование, если включено, также применяется к нему. Отсутствующий файл считается неполным бекапом, а файл с `resources: []` — корректным пустым набором.

   При повторной выгрузке файл заменяется целиком, в том числе при переходе от непустого набора к пустому, поэтому отдельных файлов удалённых ресурсов от предыдущей попытки не остаётся. Это не фиксирует первоначальный снимок между попытками: после reboot набор ресурсов может быть прочитан заново.

3. Конфигурация кесуса сохраняется как в `tools dump`: публичный `Ydb.Coordination.CreateNodeRequest` в файле `create_coordination_node.pb`, с пустым `config.path`. Конфигурация и непустой контейнер ресурсов сериализуются в текстовый protobuf через существующий `PrintProto`; для пустого набора используется явная запись `resources: []`, описанная выше. Генерация SQL не требуется. Семафоры, сессии и текущее состояние потребления ресурсов не сохраняются.

4. При включённом шифровании файловые IV формируются из IV item экспорта через `TEncryptionIV::Combine`, как в `TSchemeUploader`, с разными значениями `EBackupFileType`:

   * `create_coordination_node.pb` — `CoordinationNodeCreate`;
   * `rate_limiter_resources.pb` — `CoordinationNodeCreateRateLimiter`.

   Полученный IV явно передаётся в `AddFile` для каждого файла: без этого аргумента базовый uploader сохраняет файл без шифрования, даже если в настройках задан ключ. Для permissions и metadata используется существующая схема формирования IV.

5. Проектирование и реализация импорта выполняются отдельной задачей. Здесь фиксируется формат экспортируемых файлов, необходимый для последующего восстановления.

# Изменения

1. `TKesusSchemeUploader`

   * Реализовать новый актор на базе `TExportFilesUploader` для `ExportToS3Settings` и `ExportToFsSettings`
   * Формировать путь назначения для FS с учётом `base_path`, как в `TSchemeUploader`
   * Получать описание кесуса из SchemeShard по `SourcePathId`
   * Формировать `Ydb::Coordination::CreateNodeRequest` и файл `create_coordination_node.pb` как в `tools dump`
   * Получать все описания ресурсов одним `TEvDescribeQuoterResources` через tablet pipe
   * Обрабатывать ошибки, таймауты и отмену, закрывать пайп при завершении
   * Преобразовывать внутренние описания в `Ydb::RateLimiter::Resource` через `FillRateLimiterDescription`, сортировать по `resource_path` и собирать их в `Ydb::RateLimiter::Resources`
   * Загружать сообщение со всеми ресурсами одним файлом через общую очередь загрузки; для пустого набора явно записывать `resources: []` с завершающим переводом строки
   * При включённом шифровании явно передавать в `AddFile` разные файловые IV для конфигурации Kesus и контейнера ресурсов
2. Публичный protobuf для набора ресурсов

   * Добавить сообщение `Ydb.RateLimiter.Resources` с полем `repeated Resource resources`
   * Определить фиксированное имя файла для последующего импорта; существующий формат `tools dump` с отдельными `CreateResourceRequest` отличается
   * Расширять `TMetadata` списком ресурсов и передавать её в uploader в несериализованном виде для этого не требуется
3. `TTxProgress`

   * Создавать для кесуса `TKesusSchemeUploader` вместо `TSchemeUploader` для S3 и FS.
4. Добавить поддержку Kesus в серверные фильтры и ветки экспорта для S3 и FS, включая RPC, `TPath::IsSupportedInExports` и `IsPathTypeSchemeObject`. Изменения фильтров и команд CLI выполняются отдельной задачей.
